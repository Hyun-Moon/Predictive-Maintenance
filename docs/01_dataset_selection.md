# 데이터셋 선정 기록

> 이 문서는 "왜 이 데이터를 골랐는가"를 남기기 위한 것입니다.
> 포트폴리오에서 데이터 선정 근거는 모델 성능만큼이나 중요한 평가 요소입니다.
> (실무에서 데이터를 고르는 일이 곧 문제를 정의하는 일이기 때문입니다)

---

## 1. 선정 기준

회사 실데이터 반출이 불가능하므로 공개 데이터셋을 써야 합니다.
다만 "공개된 아무거나"가 아니라, 이 프로젝트의 질문에 답할 수 있는 데이터여야 합니다.

**이 프로젝트의 질문: "설비가 실제로 고장나기 전에, 데이터로 미리 알아챌 수 있는가?"**

이 질문에 답하려면 데이터가 다음 조건을 만족해야 합니다.

| # | 조건 | 왜 필요한가 |
|---|------|-------------|
| C1 | **다변량 시계열** | 센서 여러 개를 동시에 봐야 함. 단일 센서로는 열화를 못 잡음 |
| C2 | **개체 단위 이력** | "설비 A의 처음~끝"이 하나로 묶여야 시간에 따른 변화를 볼 수 있음 |
| C3 | **run-to-failure** | 정상 → 열화 → 고장의 전 과정이 있어야 "미리 알아챈다"를 검증 가능 |
| C4 | **운전조건 변동** | 실제 설비는 부하가 계속 바뀜. 조건 변동 없는 데이터는 현실성이 떨어짐 |
| C5 | **센서 노이즈** | 깨끗한 데이터에서만 되는 방법은 현장에서 안 됨 |
| C6 | **벤치마크 존재** | 내 성능이 좋은지 나쁜지 비교할 기준이 있어야 함 |

## 2. 후보 3개 비교

### 후보 A — NASA C-MAPSS (Turbofan Engine Degradation Simulation)

항공기 터보팬 엔진을 물리 시뮬레이터(C-MAPSS)로 돌려서 고장까지 운전시킨 데이터.
2008년 PHM 학회 경진대회용으로 공개된 이후, 예지보전 분야에서 가장 널리 쓰이는 표준 벤치마크입니다.

**실제로 내려받아 확인한 수치** (`python -m src.data.load` 출력):

| 세트 | train 행 | test 행 | train 개체 | test 개체 | 운전조건 | 고장모드 | 수명(사이클) |
|------|---------:|--------:|-----------:|----------:|:--------:|:--------:|-------------:|
| FD001 | 20,631 | 13,096 | 100 | 100 | 1개 | 1개 | 128 ~ 362 |
| FD002 | 53,759 | 33,991 | 260 | 259 | 6개 | 1개 | 128 ~ 378 |
| FD003 | 24,720 | 16,596 | 100 | 100 | 1개 | 2개 | 145 ~ 525 |
| FD004 | 61,249 | 41,214 | 249 | 248 | 6개 | 2개 | 128 ~ 543 |

- 컬럼: 개체번호 + 사이클 + 운전조건 3개 + 센서 21개 = 26개
- 각 엔진은 초기 마모 정도가 제각각인 상태에서 출발 → 실제 설비의 개체차를 모사
- train 은 고장까지 기록, test 는 고장 전에 끊김 (그 시점의 정답 RUL 이 별도 파일로 제공)

> **함정 하나**: NASA 공식 readme 에는 FD004 가 train 248 / test 249 로 적혀 있지만
> 실제 파일은 **train 249 / test 248** 입니다. `RUL_FD004.txt` 의 행 수(248)가
> test 개체 수와 일치하는 것으로 교차 확인했고, 테스트 코드에 박아두었습니다
> (`tests/test_data_load.py`). 공식 문서라도 데이터로 검증해야 한다는 사례.

| 조건 | 충족 | 비고 |
|------|:----:|------|
| C1 다변량 시계열 | O | 센서 21개 |
| C2 개체 단위 이력 | O | 엔진 100~260대 |
| C3 run-to-failure | **O** | 전 개체가 고장까지 완주 |
| C4 운전조건 변동 | O | FD002/FD004 는 6가지 조건 |
| C5 센서 노이즈 | O | 시뮬레이터가 노이즈를 주입 |
| C6 벤치마크 | **O** | 논문 수백 편, RMSE 비교 가능 |

**단점**: 실측이 아니라 시뮬레이션. 결측치·센서 고장·통신 두절이 전혀 없습니다.
그리고 도메인이 항공기 엔진이라 시설관리 직무와 표면적으로 멉니다. (→ 5장에서 다룸)

### 후보 B — MetroPT-3 (지하철 공기압축기 APU 실측 데이터)

포르투갈 포르투 지하철 차량의 **공기압축기 유닛(APU)** 에서 2020년 2~8월에
1초 간격으로 수집한 **실측** 데이터. 약 1,516만 행.

- 아날로그 센서 7개: 압축기 토출압력, 저장탱크 압력, 오일 온도, 모터 전류, 유량 등
- 디지털 신호 8개: 밸브 개폐, 압축기 ON/OFF, 부하/무부하 상태 등
- 라벨: 정비 보고서 기반 고장 구간 3건 (기간 형태로 주어짐)

| 조건 | 충족 | 비고 |
|------|:----:|------|
| C1 다변량 시계열 | O | 센서 15개 |
| C2 개체 단위 이력 | △ | 설비가 **1대뿐** — 개체 간 일반화 검증 불가 |
| C3 run-to-failure | △ | 고장이 **3건뿐**. RUL 회귀를 학습시키기엔 턱없이 부족 |
| C4 운전조건 변동 | O | 실제 운행 패턴 그대로 |
| C5 센서 노이즈 | **O** | 실측이라 결측·이상치·센서 드리프트가 그대로 |
| C6 벤치마크 | △ | 논문이 있지만 평가 방식이 제각각 |

**핵심 장점**: 압축기·압력·오일온도·모터전류 → **공조/유틸리티 설비와 물리적으로 거의 동일**합니다.
FM 직무 경력자가 "이 숫자가 무슨 의미인지" 직관적으로 설명할 수 있는 데이터입니다.

**핵심 단점**: 고장 사례가 3건뿐이라 **지도학습(RUL 회귀)이 사실상 불가능**합니다.
이상탐지(정상만 학습) 방식으로만 접근할 수 있습니다.

### 후보 C — AI4I 2020 Predictive Maintenance Dataset

UCI 저장소의 합성 데이터. 10,000행 / 14컬럼.
공기온도, 공정온도, 회전속도, 토크, 공구마모 + 고장 라벨(5가지 고장모드).

| 조건 | 충족 | 비고 |
|------|:----:|------|
| C1 다변량 시계열 | **X** | 각 행이 독립된 스냅샷. **시계열이 아님** |
| C2 개체 단위 이력 | **X** | 개체 번호가 없음 |
| C3 run-to-failure | **X** | 열화 과정이 없고 "이번 시점 고장 여부"만 있음 |
| C4 운전조건 변동 | △ | 변수는 있으나 시간 구조 없음 |
| C5 센서 노이즈 | △ | 합성 |
| C6 벤치마크 | △ | 튜토리얼용으로 많이 쓰임 |

**판정: 탈락.** 이 데이터로는 "고장을 미리 알아챈다"를 할 수 없습니다.
행 하나만 보고 고장 여부를 맞히는 **분류 문제**일 뿐, 시간에 따른 열화 추적이 불가능합니다.
입문 튜토리얼에는 좋지만, 포트폴리오에 쓰면
"시계열 예지보전과 단순 분류의 차이를 모른다"는 인상을 줄 위험이 있습니다.

## 3. 최종 선택: C-MAPSS(메인) + MetroPT-3(전이 검증)

한 개만 고르지 않고 **역할을 나눠서 둘 다** 씁니다.

```
[1단계] C-MAPSS FD001~FD004
         목적: 방법론을 제대로 만들고, 벤치마크로 성능을 객관적으로 검증
         산출: RUL 예측 모델 + 건강도 점수 + 실패 기록
                        |
                        | 같은 코드, 데이터만 교체
                        v
[2단계] MetroPT-3 (실제 압축공기 설비)
         목적: "항공기 엔진에서 만든 방법이 진짜 기계설비로 넘어가는가" 실증
         산출: 이상탐지 기반 건강도 점수 + 실제 고장 3건 사전 감지 여부
```

**이 구성의 의도**: 채용 담당자가 가장 궁금해할 질문은
"이 사람이 벤치마크 데이터만 만져본 건가, 아니면 우리 설비에도 적용할 수 있나"입니다.
2단계가 그 질문에 대한 직접적인 답이 됩니다.

### 다운로드 결과 (이 저장소 기준)

```bash
python -m src.data.download --dataset cmapss     # v 완료 (약 12MB, 자동)
python -m src.data.download --dataset metropt3   # UCI 접속 필요
```

- **C-MAPSS**: NASA S3 미러에서 자동 다운로드 성공, FD001~FD004 전부 확보 완료.
- **MetroPT-3**: UCI 서버 직접 접속이 필요합니다. 스크립트가 자동으로 수동 다운로드
  절차를 안내하도록 만들어 두었습니다. (약 500MB)

## 5. "항공기 엔진인데 왜 시설관리 포트폴리오인가" — README 서술 전략

이 프로젝트의 가장 약한 고리이자, 잘 설명하면 오히려 가장 강한 고리가 되는 지점입니다.
변명하듯 넘어가지 말고, **정면으로 다루되 구조적으로 반박**하는 방식을 권합니다.

### 전략 1: "설비가 아니라 데이터 구조가 방법론을 결정한다"

예지보전 알고리즘이 요구하는 것은 **엔진의 물리**가 아니라 **데이터의 형태**입니다.

| 알고리즘이 요구하는 것 | 항공기 엔진 | 공조기 / 펌프 |
|---|---|---|
| 다변량 시계열 | 센서 21개 | 온도·압력·유량·전류·진동 |
| 개체 단위 이력 | 엔진 1기 | 공조기 1호기 |
| 시간축 | 운전 사이클 | 운전 시간 |
| 운전조건 변동 | 고도·마하수·스로틀 | 외기온·부하율·인버터 주파수 |
| 열화 메커니즘 | 압축기 효율 저하 | 필터 막힘, 임펠러 마모, 베어링 열화 |

**핵심 문장**: "센서 이름만 바꿔 끼우면 동일한 코드가 돌아간다."
실제로 이 프로젝트는 `config/config.yaml` 에서 컬럼 이름과 경로만 바꾸면
다른 설비 데이터로 전환되도록 설계했습니다. 이것을 코드로 보여주는 것이
말로 설명하는 것보다 훨씬 설득력이 있습니다.

### 전략 2: "물리 현상이 실제로 같다"

이건 FM 경력자만 쓸 수 있는 카드입니다.

- 터보팬 엔진의 **고압 압축기**와 냉동기의 **원심 압축기**는 같은 원리로 공기/냉매를 압축합니다.
- 엔진의 **압축기 효율 저하(HPC Degradation)** = 같은 회전수에서 토출압력이 안 나오고
  토출온도가 올라가는 현상 → **냉동기 압축기 성능 저하, 펌프 임펠러 마모와 동일한 신호 패턴**
- `sensor_12 (phi = 연료유량/토출압력)` 이 상승하는 것 =
  **같은 성능을 내기 위해 더 많은 에너지를 넣고 있다**
  → 공조기에서 "같은 풍량을 내는데 전류가 올라간다"(필터 막힘)와 **정확히 같은 지표**

즉 데이터가 항공용이어도, **읽어내는 물리 신호는 시설관리에서 매일 보는 것과 같습니다.**
이 해석을 README 에 쓰면 "데이터를 도메인 지식으로 읽을 줄 아는 사람"이라는 신호가 됩니다.

### 전략 3: "오히려 더 어려운 조건에서 검증했다"

방어가 아니라 공격으로 전환하는 논리입니다.

- FD004 는 **운전조건 6가지 × 고장모드 2가지**가 섞여 있습니다.
- 대부분의 건물 설비는 운전 패턴이 이보다 단순합니다.
- **더 복잡한 조건에서 되는 방법은, 더 단순한 조건에서도 됩니다.**

### 전략 4: 한계를 먼저 인정하기 (가장 중요)

솔직하게 적는 편이 신뢰를 얻습니다. 숨기면 면접에서 반드시 질문받습니다.

**차이점 1 — 시뮬레이션 vs 실측**
C-MAPSS 에는 결측치, 센서 고장, 통신 두절, 사람의 수동 개입이 없습니다.
실제 BAS/BEMS 데이터에는 전부 있습니다.
→ **대응: MetroPT-3 실측 데이터로 2단계 검증. 결측/이상치 처리를 그 단계에서 다룸.**

**차이점 2 — 고장 이력의 부재 (이게 진짜 난관)**
C-MAPSS 는 100대가 전부 고장날 때까지 돌린 데이터입니다.
그런데 **실제 회사 설비에는 이런 데이터가 없습니다.**
예방정비 체계 하에서는 고장 전에 부품을 교체하기 때문에,
"고장까지의 전 과정"이 기록된 설비가 거의 존재하지 않습니다.

→ **대응: 그래서 이 프로젝트는 두 갈래로 갑니다.**

| 접근 | 필요한 것 | 현장 적용성 |
|------|-----------|-------------|
| **RUL 회귀** (지도학습) | 고장 이력 다수 | 낮음 — 데이터가 없음 |
| **이상탐지 + 건강도 점수** (비지도) | **정상 데이터만** | **높음 — 어느 현장에나 있음** |

**RUL 회귀는 방법론 검증용이고, 실제로 회사에 들고 갈 수 있는 것은 이상탐지 쪽입니다.**
이 구분을 명확히 쓰는 것이 이 포트폴리오의 핵심 메시지가 되어야 합니다.
"벤치마크 점수 잘 나왔다"보다 훨씬 실무적인 이야기이기 때문입니다.

**차이점 3 — 시간 해상도**
C-MAPSS 의 1 사이클은 비행 1회(수 시간)입니다.
BAS 데이터는 보통 1~15분 간격입니다.
→ 대응: 절대 시간 단위에 의존하지 않고 **"수명 대비 진행률(%)"** 로 정규화해 다룹니다.
