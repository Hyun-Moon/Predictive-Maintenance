# 실험 기록 — 시도한 것, 실패한 것, 배운 것

> 이 문서는 **프로젝트를 진행하면서 실시간으로 계속 추가**합니다.
> 최종 README 의 "시도했지만 실패한 것들" 섹션은 여기서 뽑아 씁니다.
>
> **왜 실패를 기록하나?**
> 성공한 결과만 있는 포트폴리오는 "운이 좋았는지 실력인지" 구분이 안 됩니다.
> 무엇을 왜 버렸는지가 적혀 있으면, 판단 과정 자체가 실력의 증거가 됩니다.
> 실무에서도 "이건 이미 해봤는데 안 됐다"는 기록이 가장 값진 자산입니다.

기록 형식:
- **[시도]** 무엇을 했는가
- **[결과]** 어떻게 됐는가 (숫자로)
- **[원인]** 왜 그랬는가
- **[배운 것]** 다음에 어떻게 할 것인가

## 0단계 — 데이터셋 선정 및 환경 구축

### 0-1. AI4I 2020 데이터셋 검토 후 탈락 — 실패한 선택

- **[시도]** 예지보전 입문용으로 가장 많이 보이는 UCI AI4I 2020 데이터셋(10,000행)을
  메인 후보로 검토.
- **[결과]** 탈락.
- **[원인]** 각 행이 **독립된 스냅샷**이고 개체 번호도 시간축도 없었음.
  즉 시계열이 아니라 단순 분류용 표 데이터. 이 데이터로는 RUL 을 정의할 수조차 없음.
  "고장을 미리 알아챈다"가 아니라 "지금 고장인지 맞힌다"가 되어버림.
- **[배운 것]** 예지보전 데이터셋이라는 이름이 붙어 있다고 다 시계열이 아니다.
  데이터를 고를 때 **"내 질문에 답할 수 있는 구조인가"를 먼저 확인**해야 한다.
  구체적으로는 `(개체 ID, 시간, 센서들)` 세 축이 다 있는지부터 본다.

### 0-2. 다운로드 미러 1번(PHM Society) 접속 실패

- **[시도]** `data.phmsociety.org` 의 NASA 미러에서 C-MAPSS 자동 다운로드.
- **[결과]** `ProxyError: Tunnel connection failed: 403 Forbidden`.
- **[원인]** 실행 환경의 네트워크 정책이 해당 도메인을 차단.
- **[배운 것]** 다운로드 스크립트는 **미러를 여러 개 두고 순차 시도**해야 한다.
  2번 미러(`phm-datasets.s3.amazonaws.com`)로 성공.
  또한 전부 실패했을 때 **수동 다운로드 절차를 자동으로 안내**하도록 만들어 두면,
  나중에 사내망에서 이 저장소를 clone 하는 사람이 막히지 않는다.
  (`src/data/download.py` 의 `print_manual_instructions`)

### 0-3. NASA 공식 문서의 오류 발견 — 문서를 믿지 말 것

- **[시도]** NASA `readme.txt` 에 적힌 개체 수를 그대로 테스트 코드에 넣음.
  (FD004: train 248 / test 249)
- **[결과]** 테스트 실패. 실제 데이터는 **train 249 / test 248** 이었음.
- **[원인]** 공식 readme 의 오타. train/test 숫자가 서로 바뀌어 있음.
  `RUL_FD004.txt` 의 행 수가 248 인 것으로 교차 확인 — RUL 파일은 test 개체마다
  한 줄씩이므로, test 개체가 248 인 것이 맞음.
- **[배운 것]** **공식 문서라도 데이터로 검증한다.** 그리고 검증 결과를 테스트 코드에
  박아두면(`tests/test_data_load.py`) 나중에 같은 착각을 반복하지 않는다.
  이런 교차 검증(RUL 파일 행 수 ↔ test 개체 수)을 습관화할 것.

### 0-4. 원본 txt 파싱 — 줄 끝 공백 함정

- **[시도]** `pd.read_csv(path, sep=" ", header=None)` 으로 원본 읽기.
- **[결과]** 컬럼이 26개가 아니라 28개로 읽힘. 뒤 2개는 전부 NaN.
- **[원인]** 원본 파일의 **각 줄 끝에 공백이 2개** 붙어 있음.
  `sep=" "` 는 공백 하나를 정확히 구분자로 보므로, 끝의 공백 2개가 빈 컬럼 2개를 만듦.
- **[배운 것]** 공백 구분 텍스트는 `sep=" "` 가 아니라 **`sep=r"\s+"`** 를 쓴다.
  (공백이 몇 개든 하나의 구분자로 취급)
  그리고 파싱 직후 **컬럼 수를 명시적으로 검사**하는 코드를 넣어두면
  이런 문제를 조용히 넘어가지 않는다. (`_read_raw` 의 `ValueError` 체크)

### 0-5. .gitignore 가 소스코드 폴더를 삼킴

- **[시도]** 학습된 모델 파일을 git 에서 제외하려고 `.gitignore` 에 `models/` 를 추가.
- **[결과]** `git add` 후 목록을 확인해 보니 **`src/models/` 폴더가 통째로 빠져 있었음.**
- **[원인]** `.gitignore` 에서 `models/` 는 "이름이 models 인 모든 폴더"를 의미합니다.
  최상위 `models/` 뿐 아니라 소스코드 폴더인 `src/models/` 까지 매칭됨.
  최상위만 지정하려면 앞에 슬래시를 붙여 **`/models/`** 로 써야 합니다.
- **[배운 것]** `git add` 후에는 반드시 `git status` 로 **실제로 무엇이 올라가는지 눈으로 확인**한다.
  빠진 파일은 에러를 내지 않고 조용히 사라지기 때문에, 확인하지 않으면
  나중에 clone 했을 때 `ModuleNotFoundError` 로 뒤늦게 발견하게 된다.
  특정 파일이 왜 무시되는지 확인: `git check-ignore -v <파일경로>`

## 1단계 — EDA

### 1-1. `std() == 0` 으로 상수 컬럼을 찾다가 2개를 놓침

- **[시도]** 값이 안 변하는 센서를 걸러내려고 `df[c].std() == 0` 으로 검사.
- **[결과]** 4개만 잡힘. 그런데 `nunique()` 로 보니 **상수인 센서가 6개**였음.
  S05(전부 14.62), S16(전부 0.03) 이 빠져나감.
- **[원인]** 부동소수점 누적 오차. 값이 전부 똑같아도 2만 건을 더하고 나누는 과정에서
  오차가 쌓여 표준편차가 `5.3e-15`, `3.5e-18` 로 나옴. 0 이 아니므로 조건에 안 걸림.
- **[배운 것]** 소수 비교에 `== 0` 을 쓰지 않는다. **허용치를 둔다.**
  (`src/features/select.py` 의 `DEFAULT_TOL = 1e-9`)
  그리고 표준편차와 고유값 개수를 **둘 다** 봐야 한다. 한쪽만 보면 반드시 놓친다.

### 1-2. "센서 하나로 AUC 0.99" 를 성과로 착각할 뻔함 — 평가 설계의 실패

- **[시도]** 정상(RUL>125)과 고장임박(RUL≤30)을 센서 하나로 구분해 보고
  AUC 0.994 를 얻음. 처음엔 "좋은 결과"로 기록하려 함.
- **[결과]** 사실상 의미 없는 성과였음.
- **[원인]** 비교한 두 구간이 시간상 너무 멀리 떨어져 있었음.
  단조 증가하는 센서라면 당연히 갈립니다. 게다가 **RUL 30 에서 알아채봐야 이미 늦음**.
  즉 문제를 쉽게 만들어놓고 잘 풀었다고 한 셈.
- **[배운 것]** **평가 설정이 성능 숫자보다 먼저다.**
  "무엇을 맞히면 실제로 쓸모가 있는가"를 정하고 나서 지표를 봐야 한다.
  이 착각을 알아채고 조기 탐지 곡선(RUL 구간별 AUC)으로 평가를 다시 설계했더니
  RUL 100~125 구간에서 **AUC 0.62** 라는 진짜 성적표가 나왔다.

### 1-3. 이동평균으로 노이즈를 없애면 조기 탐지가 될 줄 알았는데 — 거의 효과 없음

- **[시도]** 조기 탐지가 안 되는 이유가 센서 노이즈라고 보고,
  설비별 이동평균(창 1 / 5 / 15 / 30 사이클)을 걸어 RUL 100~125 구간 AUC 를 측정.
- **[결과]** 거의 개선되지 않음. 오히려 창을 키우면 다시 나빠짐.

  | 이동평균 창 | AUC |
  |---|---|
  | 1 (원본) | 0.624 |
  | 5 | 0.640 |
  | 15 | 0.634 |
  | 30 | 0.625 |

- **[원인]** 노이즈는 애초에 주된 원인이 아니었음.
  신호대잡음비를 재보니 열화폭이 노이즈의 **6~8배**였다.
  창을 너무 키우면 이번엔 열화 신호 자체가 뭉개져서 다시 나빠진다.
- **[배운 것]** **원인을 진단하기 전에 대책부터 적용하지 말 것.**
  "노이즈가 문제일 것"은 검증되지 않은 추측이었다.
  신호대잡음비를 먼저 쟀다면 이 시도를 안 했을 것이다.

### 1-4. 개체별 baseline 보정 — 절반만 성공

- **[시도]** 1-3 이 실패한 뒤 원인을 다시 조사했더니,
  **엔진마다 출발점이 달라서 열화폭의 77% 에 해당하는 개체차**가 있었음.
  그래서 설비별 초기 20사이클 평균을 빼서 "자기 자신 대비 편차"로 바꿔 재측정.
  (평가 시 baseline 구간은 제외해 순환논리를 피함)
- **[결과]** 구간별로 결과가 갈림.

  | RUL 구간 | 원본 | baseline 보정 | 개선 |
  |---|---|---|---|
  | 50~75 | 0.819 | 0.866 | **+0.048** |
  | 75~100 | 0.697 | 0.728 | **+0.031** |
  | 100~125 | 0.614 | 0.616 | +0.002 |

- **[원인]** 중간 구간에서는 개체차 제거가 실제로 도움이 된다.
  하지만 **가장 이른 구간에서는 전혀 도움이 안 된다.**
  그 시점에는 열화가 아직 일어나지 않아 **제거할 개체차는 있어도 드러낼 신호가 없기 때문**.
- **[배운 것]** 전처리로 없앨 수 있는 것은 **가려진 신호**이지 **없는 신호**가 아니다.
  RUL 100 이전 구간에는 물리적으로 신호가 거의 존재하지 않으므로,
  이 프로젝트의 현실적인 탐지 한계는 **RUL 75~100 부근**으로 잡는 것이 정직하다.
  → 2단계 목표를 "RUL 125부터 잡겠다"가 아니라
    "RUL 50~100 구간의 AUC 를 다변량 결합으로 얼마나 올리는가"로 설정한다.

## 2단계 — 건강도 점수 / 이상탐지

### 2-1. PCA 재구성오차가 완전히 실패 — 원인은 흔히 쓰는 기본값이었다

- **[시도]** 정상 데이터로 PCA 를 학습해 재구성 오차를 이상 점수로 사용.
  주성분 개수는 관행적으로 **"분산의 95%를 담는 만큼"** 으로 지정.
- **[결과]** **AUC 0.529.** 동전던지기(0.5)와 다를 바 없었음.
  다른 방법들이 0.72~0.75 를 낼 때 혼자 바닥이었고,
  전처리를 개선해 다른 방법이 전부 0.93 대로 오를 때도 **0.708 에 머물렀음.**
- **[원인]** 주성분이 몇 개 뽑혔는지 확인해 보니 **14개 중 12~13개**였다.
  거의 압축을 안 한 것이다. 압축을 안 하면 무엇을 넣어도 그대로 복원되므로
  재구성 오차가 항상 0 에 가깝고, 이상 신호가 오차에 나타날 수 없다.
  이 데이터의 센서들은 정상 구간에서 서로 그리 강하게 상관되지 않아서,
  분산 95% 를 채우려면 노이즈 차원까지 전부 담아야 했던 것.
- **[재시도]** 주성분 개수를 직접 지정해 다시 측정.

  | 주성분 수 | AUC |
  |---|---|
  | 1 | **0.940** |
  | 2 | 0.939 |
  | 3 | 0.927 |
  | 5 | 0.925 |
  | 8 | 0.914 |
  | 분산95% (12~13개) | 0.708 |

- **[배운 것]** **"관행적인 기본값"이 가장 위험한 설정일 수 있다.**
  PCA 를 이상탐지에 쓸 때는 분산 비율이 아니라
  **"정상의 큰 줄기만 남기도록 주성분을 강하게 제한"** 해야 한다.
  그리고 성능이 이상하면 지표만 보지 말고
  **모델이 내부적으로 무엇을 하고 있는지(주성분을 몇 개 골랐는지) 찍어봐야 한다.**
  이 한 줄을 출력해 보는 데 1분 걸렸고, 그게 원인 진단의 전부였다.

### 2-2. 건강도 점수 스케일 오설계 — 멀쩡한 설비가 75점에서 시작함

- **[시도]** 이상 점수(거리)를 0~100 으로 바꾸면서
  `HI = 100 × 0.5 ^ (d / d_경보)` 라는 식을 사용.
  "거리가 0 이면 완전 정상이니 100점" 이라는 생각이었음.
- **[결과]** 궤적 그림을 그려 보니 **정상 구간의 건강도가 처음부터 75점**이었다.
  100 에서 출발해 떨어지는 그림이 나와야 하는데 그렇지 않았음.
- **[원인]** 정상 상태의 거리는 0 이 아니다. 이 데이터에서는 중앙값이 **2.82** 였고
  경보 기준점은 6.88 이었다. 식에 넣으면 `0.5^(2.82/6.88) = 0.75` → 75점.
  즉 **기준점을 하나만 잡아서 생긴 문제.**
  정상이 이미 75점이면 경보선(50점)까지 여유가 25점뿐이라
  약간만 흔들려도 경보에 닿게 된다.
- **[수정]** 기준점을 두 개로 바꿈.
  `HI = 100 × 0.5 ^ ((d - d_정상) / (d_경보 - d_정상))`
  → 정상 중앙값이 정확히 100점, 경보 기준점이 정확히 50점이 된다.
- **[배운 것]** 점수를 만들 때는 **양 끝점이 무엇을 뜻하는지 먼저 정하고 식을 세운다.**
  그리고 숫자만 보지 말고 **궤적을 그려봐야 한다.**
  AUC 는 순위만 보는 지표라 이 문제를 전혀 잡아내지 못했다.
  (실제로 이 수정 전후 AUC 와 오경보율은 **완전히 동일했다** — 단조 변환이므로.
   지표는 그대로인데 **읽을 수 있는 점수인가**만 달라진 것이다)

### 2-3. 1단계 결론을 수정 — 이동평균은 "쓸모없다"가 아니라 "순서가 있다"

- **[시도]** 1단계에서 이동평균이 거의 효과가 없어(0.624 → 0.640)
  "노이즈는 주범이 아니다"라고 결론지었음. 이번 단계에서 다시 측정.
- **[결과]** 조건에 따라 효과가 크게 갈렸다.

  | 조건 | 이동평균 적용 전 → 후 |
  |---|---|
  | 원본에 적용 | 0.718 → 0.755 (+0.037) |
  | **개체차 보정 후 적용** | 0.890 → **0.943 (+0.053)** |

- **[원인]** 개체차(열화폭의 77%)라는 큰 오차가 남아 있는 상태에서
  노이즈(12~16%)를 다듬어봐야 전체 성능에는 티가 나지 않는다.
  **큰 것을 먼저 걷어내야 작은 것이 보인다.**
- **[배운 것]** 전처리 기법의 효과는 단독으로 평가하면 안 된다.
  **적용 순서에 따라 결론이 뒤집힌다.**
  1단계 문서의 "이동평균은 효과 없음" 결론을
  "개체차 보정 이후에 적용해야 효과가 있음"으로 수정했다.

### 2-4. "오경보율 15.8%" 를 그냥 실패로 적을 뻔함

- **[시도]** 경보 규칙을 만들고 정상 구간(RUL>125)에서의 오경보율을 측정 → **15.8%.**
  현장 기준으로 너무 높아 실패로 기록하려 했음.
- **[결과]** 구간별 이상 점수 중앙값을 찍어보니 해석이 달라졌다.

  | 구간 | 이상 점수 중앙값 |
  |---|---|
  | 학습 구간 (cycle ≤ 30) | 2.82 |
  | 정상 평가 구간 cycle 31~60 | 3.72 |
  | 정상 평가 구간 cycle 61+ | 5.67 |

  "정상"이라 라벨한 구간 안에서도 점수가 이미 단조 상승하고 있었다.
- **[원인]** RUL 125 라는 경계는 편의상 정한 값이지 물리적 경계가 아니다.
  15.8% 중 상당 부분은 모델이 틀린 게 아니라
  **실제로 열화가 시작됐는데 라벨이 정상이라고 부른 것**일 수 있다.
- **[배운 것]** **지표가 나쁘게 나왔을 때 모델부터 의심하지 말고
  라벨 정의가 타당한지 먼저 확인한다.**
  다만 그렇다고 15.8% 를 정당화하고 넘어가지는 않았고,
  지속 조건(디바운스)을 도입해 5.8% 까지 낮추는 트레이드오프 표를 만들어
  **선택은 현장이 하도록** 남겼다.
