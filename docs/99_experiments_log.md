# 실험 기록 — 시도한 것, 실패한 것, 배운 것

> 이 문서는 **프로젝트를 진행하면서 실시간으로 계속 추가**합니다.
> 최종 README 의 "시도했지만 실패한 것들" 섹션은 여기서 뽑아 씁니다.
>
> **왜 실패를 기록하나?**
> 성공한 결과만 있는 포트폴리오는 "운이 좋았는지 실력인지" 구분이 안 됩니다.
> 무엇을 왜 버렸는지가 적혀 있으면, 판단 과정 자체가 실력의 증거가 됩니다.
> 실무에서도 "이건 이미 해봤는데 안 됐다"는 기록이 가장 값진 자산입니다.

기록 형식:
- **[시도]** 무엇을 했는가
- **[결과]** 어떻게 됐는가 (숫자로)
- **[원인]** 왜 그랬는가
- **[배운 것]** 다음에 어떻게 할 것인가

## 0단계 — 데이터셋 선정 및 환경 구축

### 0-1. AI4I 2020 데이터셋 검토 후 탈락 — 실패한 선택

- **[시도]** 예지보전 입문용으로 가장 많이 보이는 UCI AI4I 2020 데이터셋(10,000행)을
  메인 후보로 검토.
- **[결과]** 탈락.
- **[원인]** 각 행이 **독립된 스냅샷**이고 개체 번호도 시간축도 없었음.
  즉 시계열이 아니라 단순 분류용 표 데이터. 이 데이터로는 RUL 을 정의할 수조차 없음.
  "고장을 미리 알아챈다"가 아니라 "지금 고장인지 맞힌다"가 되어버림.
- **[배운 것]** 예지보전 데이터셋이라는 이름이 붙어 있다고 다 시계열이 아니다.
  데이터를 고를 때 **"내 질문에 답할 수 있는 구조인가"를 먼저 확인**해야 한다.
  구체적으로는 `(개체 ID, 시간, 센서들)` 세 축이 다 있는지부터 본다.

### 0-2. 다운로드 미러 1번(PHM Society) 접속 실패

- **[시도]** `data.phmsociety.org` 의 NASA 미러에서 C-MAPSS 자동 다운로드.
- **[결과]** `ProxyError: Tunnel connection failed: 403 Forbidden`.
- **[원인]** 실행 환경의 네트워크 정책이 해당 도메인을 차단.
- **[배운 것]** 다운로드 스크립트는 **미러를 여러 개 두고 순차 시도**해야 한다.
  2번 미러(`phm-datasets.s3.amazonaws.com`)로 성공.
  또한 전부 실패했을 때 **수동 다운로드 절차를 자동으로 안내**하도록 만들어 두면,
  나중에 사내망에서 이 저장소를 clone 하는 사람이 막히지 않는다.
  (`src/data/download.py` 의 `print_manual_instructions`)

### 0-3. NASA 공식 문서의 오류 발견 — 문서를 믿지 말 것

- **[시도]** NASA `readme.txt` 에 적힌 개체 수를 그대로 테스트 코드에 넣음.
  (FD004: train 248 / test 249)
- **[결과]** 테스트 실패. 실제 데이터는 **train 249 / test 248** 이었음.
- **[원인]** 공식 readme 의 오타. train/test 숫자가 서로 바뀌어 있음.
  `RUL_FD004.txt` 의 행 수가 248 인 것으로 교차 확인 — RUL 파일은 test 개체마다
  한 줄씩이므로, test 개체가 248 인 것이 맞음.
- **[배운 것]** **공식 문서라도 데이터로 검증한다.** 그리고 검증 결과를 테스트 코드에
  박아두면(`tests/test_data_load.py`) 나중에 같은 착각을 반복하지 않는다.
  이런 교차 검증(RUL 파일 행 수 ↔ test 개체 수)을 습관화할 것.

### 0-4. 원본 txt 파싱 — 줄 끝 공백 함정

- **[시도]** `pd.read_csv(path, sep=" ", header=None)` 으로 원본 읽기.
- **[결과]** 컬럼이 26개가 아니라 28개로 읽힘. 뒤 2개는 전부 NaN.
- **[원인]** 원본 파일의 **각 줄 끝에 공백이 2개** 붙어 있음.
  `sep=" "` 는 공백 하나를 정확히 구분자로 보므로, 끝의 공백 2개가 빈 컬럼 2개를 만듦.
- **[배운 것]** 공백 구분 텍스트는 `sep=" "` 가 아니라 **`sep=r"\s+"`** 를 쓴다.
  (공백이 몇 개든 하나의 구분자로 취급)
  그리고 파싱 직후 **컬럼 수를 명시적으로 검사**하는 코드를 넣어두면
  이런 문제를 조용히 넘어가지 않는다. (`_read_raw` 의 `ValueError` 체크)

### 0-5. .gitignore 가 소스코드 폴더를 삼킴

- **[시도]** 학습된 모델 파일을 git 에서 제외하려고 `.gitignore` 에 `models/` 를 추가.
- **[결과]** `git add` 후 목록을 확인해 보니 **`src/models/` 폴더가 통째로 빠져 있었음.**
- **[원인]** `.gitignore` 에서 `models/` 는 "이름이 models 인 모든 폴더"를 의미합니다.
  최상위 `models/` 뿐 아니라 소스코드 폴더인 `src/models/` 까지 매칭됨.
  최상위만 지정하려면 앞에 슬래시를 붙여 **`/models/`** 로 써야 합니다.
- **[배운 것]** `git add` 후에는 반드시 `git status` 로 **실제로 무엇이 올라가는지 눈으로 확인**한다.
  빠진 파일은 에러를 내지 않고 조용히 사라지기 때문에, 확인하지 않으면
  나중에 clone 했을 때 `ModuleNotFoundError` 로 뒤늦게 발견하게 된다.
  특정 파일이 왜 무시되는지 확인: `git check-ignore -v <파일경로>`

## 1단계 — EDA

### 1-1. `std() == 0` 으로 상수 컬럼을 찾다가 2개를 놓침

- **[시도]** 값이 안 변하는 센서를 걸러내려고 `df[c].std() == 0` 으로 검사.
- **[결과]** 4개만 잡힘. 그런데 `nunique()` 로 보니 **상수인 센서가 6개**였음.
  S05(전부 14.62), S16(전부 0.03) 이 빠져나감.
- **[원인]** 부동소수점 누적 오차. 값이 전부 똑같아도 2만 건을 더하고 나누는 과정에서
  오차가 쌓여 표준편차가 `5.3e-15`, `3.5e-18` 로 나옴. 0 이 아니므로 조건에 안 걸림.
- **[배운 것]** 소수 비교에 `== 0` 을 쓰지 않는다. **허용치를 둔다.**
  (`src/features/select.py` 의 `DEFAULT_TOL = 1e-9`)
  그리고 표준편차와 고유값 개수를 **둘 다** 봐야 한다. 한쪽만 보면 반드시 놓친다.

### 1-2. "센서 하나로 AUC 0.99" 를 성과로 착각할 뻔함 — 평가 설계의 실패

- **[시도]** 정상(RUL>125)과 고장임박(RUL≤30)을 센서 하나로 구분해 보고
  AUC 0.994 를 얻음. 처음엔 "좋은 결과"로 기록하려 함.
- **[결과]** 사실상 의미 없는 성과였음.
- **[원인]** 비교한 두 구간이 시간상 너무 멀리 떨어져 있었음.
  단조 증가하는 센서라면 당연히 갈립니다. 게다가 **RUL 30 에서 알아채봐야 이미 늦음**.
  즉 문제를 쉽게 만들어놓고 잘 풀었다고 한 셈.
- **[배운 것]** **평가 설정이 성능 숫자보다 먼저다.**
  "무엇을 맞히면 실제로 쓸모가 있는가"를 정하고 나서 지표를 봐야 한다.
  이 착각을 알아채고 조기 탐지 곡선(RUL 구간별 AUC)으로 평가를 다시 설계했더니
  RUL 100~125 구간에서 **AUC 0.62** 라는 진짜 성적표가 나왔다.

### 1-3. 이동평균으로 노이즈를 없애면 조기 탐지가 될 줄 알았는데 — 거의 효과 없음

- **[시도]** 조기 탐지가 안 되는 이유가 센서 노이즈라고 보고,
  설비별 이동평균(창 1 / 5 / 15 / 30 사이클)을 걸어 RUL 100~125 구간 AUC 를 측정.
- **[결과]** 거의 개선되지 않음. 오히려 창을 키우면 다시 나빠짐.

  | 이동평균 창 | AUC |
  |---|---|
  | 1 (원본) | 0.624 |
  | 5 | 0.640 |
  | 15 | 0.634 |
  | 30 | 0.625 |

- **[원인]** 노이즈는 애초에 주된 원인이 아니었음.
  신호대잡음비를 재보니 열화폭이 노이즈의 **6~8배**였다.
  창을 너무 키우면 이번엔 열화 신호 자체가 뭉개져서 다시 나빠진다.
- **[배운 것]** **원인을 진단하기 전에 대책부터 적용하지 말 것.**
  "노이즈가 문제일 것"은 검증되지 않은 추측이었다.
  신호대잡음비를 먼저 쟀다면 이 시도를 안 했을 것이다.

### 1-4. 개체별 baseline 보정 — 절반만 성공

- **[시도]** 1-3 이 실패한 뒤 원인을 다시 조사했더니,
  **엔진마다 출발점이 달라서 열화폭의 77% 에 해당하는 개체차**가 있었음.
  그래서 설비별 초기 20사이클 평균을 빼서 "자기 자신 대비 편차"로 바꿔 재측정.
  (평가 시 baseline 구간은 제외해 순환논리를 피함)
- **[결과]** 구간별로 결과가 갈림.

  | RUL 구간 | 원본 | baseline 보정 | 개선 |
  |---|---|---|---|
  | 50~75 | 0.819 | 0.866 | **+0.048** |
  | 75~100 | 0.697 | 0.728 | **+0.031** |
  | 100~125 | 0.614 | 0.616 | +0.002 |

- **[원인]** 중간 구간에서는 개체차 제거가 실제로 도움이 된다.
  하지만 **가장 이른 구간에서는 전혀 도움이 안 된다.**
  그 시점에는 열화가 아직 일어나지 않아 **제거할 개체차는 있어도 드러낼 신호가 없기 때문**.
- **[배운 것]** 전처리로 없앨 수 있는 것은 **가려진 신호**이지 **없는 신호**가 아니다.
  RUL 100 이전 구간에는 물리적으로 신호가 거의 존재하지 않으므로,
  이 프로젝트의 현실적인 탐지 한계는 **RUL 75~100 부근**으로 잡는 것이 정직하다.
  → 2단계 목표를 "RUL 125부터 잡겠다"가 아니라
    "RUL 50~100 구간의 AUC 를 다변량 결합으로 얼마나 올리는가"로 설정한다.

## 2단계 — 건강도 점수 / 이상탐지

### 2-1. PCA 재구성오차가 완전히 실패 — 원인은 흔히 쓰는 기본값이었다

- **[시도]** 정상 데이터로 PCA 를 학습해 재구성 오차를 이상 점수로 사용.
  주성분 개수는 관행적으로 **"분산의 95%를 담는 만큼"** 으로 지정.
- **[결과]** **AUC 0.529.** 동전던지기(0.5)와 다를 바 없었음.
  다른 방법들이 0.72~0.75 를 낼 때 혼자 바닥이었고,
  전처리를 개선해 다른 방법이 전부 0.93 대로 오를 때도 **0.708 에 머물렀음.**
- **[원인]** 주성분이 몇 개 뽑혔는지 확인해 보니 **14개 중 12~13개**였다.
  거의 압축을 안 한 것이다. 압축을 안 하면 무엇을 넣어도 그대로 복원되므로
  재구성 오차가 항상 0 에 가깝고, 이상 신호가 오차에 나타날 수 없다.
  이 데이터의 센서들은 정상 구간에서 서로 그리 강하게 상관되지 않아서,
  분산 95% 를 채우려면 노이즈 차원까지 전부 담아야 했던 것.
- **[재시도]** 주성분 개수를 직접 지정해 다시 측정.

  | 주성분 수 | AUC |
  |---|---|
  | 1 | **0.940** |
  | 2 | 0.939 |
  | 3 | 0.927 |
  | 5 | 0.925 |
  | 8 | 0.914 |
  | 분산95% (12~13개) | 0.708 |

- **[배운 것]** **"관행적인 기본값"이 가장 위험한 설정일 수 있다.**
  PCA 를 이상탐지에 쓸 때는 분산 비율이 아니라
  **"정상의 큰 줄기만 남기도록 주성분을 강하게 제한"** 해야 한다.
  그리고 성능이 이상하면 지표만 보지 말고
  **모델이 내부적으로 무엇을 하고 있는지(주성분을 몇 개 골랐는지) 찍어봐야 한다.**
  이 한 줄을 출력해 보는 데 1분 걸렸고, 그게 원인 진단의 전부였다.

### 2-2. 건강도 점수 스케일 오설계 — 멀쩡한 설비가 75점에서 시작함

- **[시도]** 이상 점수(거리)를 0~100 으로 바꾸면서
  `HI = 100 × 0.5 ^ (d / d_경보)` 라는 식을 사용.
  "거리가 0 이면 완전 정상이니 100점" 이라는 생각이었음.
- **[결과]** 궤적 그림을 그려 보니 **정상 구간의 건강도가 처음부터 75점**이었다.
  100 에서 출발해 떨어지는 그림이 나와야 하는데 그렇지 않았음.
- **[원인]** 정상 상태의 거리는 0 이 아니다. 이 데이터에서는 중앙값이 **2.82** 였고
  경보 기준점은 6.88 이었다. 식에 넣으면 `0.5^(2.82/6.88) = 0.75` → 75점.
  즉 **기준점을 하나만 잡아서 생긴 문제.**
  정상이 이미 75점이면 경보선(50점)까지 여유가 25점뿐이라
  약간만 흔들려도 경보에 닿게 된다.
- **[수정]** 기준점을 두 개로 바꿈.
  `HI = 100 × 0.5 ^ ((d - d_정상) / (d_경보 - d_정상))`
  → 정상 중앙값이 정확히 100점, 경보 기준점이 정확히 50점이 된다.
- **[배운 것]** 점수를 만들 때는 **양 끝점이 무엇을 뜻하는지 먼저 정하고 식을 세운다.**
  그리고 숫자만 보지 말고 **궤적을 그려봐야 한다.**
  AUC 는 순위만 보는 지표라 이 문제를 전혀 잡아내지 못했다.
  (실제로 이 수정 전후 AUC 와 오경보율은 **완전히 동일했다** — 단조 변환이므로.
   지표는 그대로인데 **읽을 수 있는 점수인가**만 달라진 것이다)

### 2-3. 1단계 결론을 수정 — 이동평균은 "쓸모없다"가 아니라 "순서가 있다"

- **[시도]** 1단계에서 이동평균이 거의 효과가 없어(0.624 → 0.640)
  "노이즈는 주범이 아니다"라고 결론지었음. 이번 단계에서 다시 측정.
- **[결과]** 조건에 따라 효과가 크게 갈렸다.

  | 조건 | 이동평균 적용 전 → 후 |
  |---|---|
  | 원본에 적용 | 0.718 → 0.755 (+0.037) |
  | **개체차 보정 후 적용** | 0.890 → **0.943 (+0.053)** |

- **[원인]** 개체차(열화폭의 77%)라는 큰 오차가 남아 있는 상태에서
  노이즈(12~16%)를 다듬어봐야 전체 성능에는 티가 나지 않는다.
  **큰 것을 먼저 걷어내야 작은 것이 보인다.**
- **[배운 것]** 전처리 기법의 효과는 단독으로 평가하면 안 된다.
  **적용 순서에 따라 결론이 뒤집힌다.**
  1단계 문서의 "이동평균은 효과 없음" 결론을
  "개체차 보정 이후에 적용해야 효과가 있음"으로 수정했다.

### 2-4. "오경보율 15.8%" 를 그냥 실패로 적을 뻔함

- **[시도]** 경보 규칙을 만들고 정상 구간(RUL>125)에서의 오경보율을 측정 → **15.8%.**
  현장 기준으로 너무 높아 실패로 기록하려 했음.
- **[결과]** 구간별 이상 점수 중앙값을 찍어보니 해석이 달라졌다.

  | 구간 | 이상 점수 중앙값 |
  |---|---|
  | 학습 구간 (cycle ≤ 30) | 2.82 |
  | 정상 평가 구간 cycle 31~60 | 3.72 |
  | 정상 평가 구간 cycle 61+ | 5.67 |

  "정상"이라 라벨한 구간 안에서도 점수가 이미 단조 상승하고 있었다.
- **[원인]** RUL 125 라는 경계는 편의상 정한 값이지 물리적 경계가 아니다.
  15.8% 중 상당 부분은 모델이 틀린 게 아니라
  **실제로 열화가 시작됐는데 라벨이 정상이라고 부른 것**일 수 있다.
- **[배운 것]** **지표가 나쁘게 나왔을 때 모델부터 의심하지 말고
  라벨 정의가 타당한지 먼저 확인한다.**
  다만 그렇다고 15.8% 를 정당화하고 넘어가지는 않았고,
  지속 조건(디바운스)을 도입해 5.8% 까지 낮추는 트레이드오프 표를 만들어
  **선택은 현장이 하도록** 남겼다.

## 3단계 — RUL 예측 모델

### 3-1. 성능이 너무 좋아서 의심함 — 누수 검증을 먼저 돌림

- **[시도]** 특징을 다 넣고 LightGBM 을 학습했더니 시험 RMSE **9.07** 이 나왔다.
  공개 논문에서 보고되는 FD001 성적이 대체로 12~16 인데 그보다 좋았다.
- **[결과]** 기뻐하기 전에 누수부터 검증. 두 가지를 확인했다.
  1. **라벨을 무작위로 섞고 재학습** → RMSE 39.63 (기준선 40.51 수준).
     누수가 있었다면 라벨을 섞어도 성능이 남는다. 남지 않았으므로 누수 없음.
  2. **검증 점수와 시험 점수 비교** → 검증 9.0 / 시험 10.5.
     시험이 약간 나쁜 것이 정상. (시험이 더 좋으면 오히려 이상한 것)
- **[배운 것]** **성능이 예상보다 좋으면 그것 자체가 점검 신호다.**
  비정상적으로 좋은 성능의 가장 흔한 원인은 실력이 아니라 데이터 누수다.
  라벨 셔플 테스트는 5분이면 끝나고 대부분의 누수를 잡아낸다.

  그리고 검증 결과와 별개로, **논문과 직접 비교하지는 않기로 했다.**
  (1) 정답 상한 처리가 논문마다 다르다 — 125로 자르면 9.07, 안 자르면 10.29.
  (2) 이 프로젝트는 시험 설비의 초기 30사이클로 기준선을 잡는데,
      라벨을 쓰지 않으니 반칙은 아니지만 일반적인 논문 방식보다 정보를 더 쓴다.
  → "논문보다 좋다"가 아니라 **"이 평가 조건에서 이 숫자가 나왔다"** 로만 적었다.

### 3-2. 검증 점수와 시험 점수가 섞여 무엇과 비교하는지 알 수 없게 됨

- **[시도]** 처음에는 모델을 한 번만 학습시켰다.
  학습 80% 로 모델을 만들고, 그 모델로 검증 점수와 시험 점수를 모두 냈다.
  그런데 최종 예측 그림은 학습 100% 로 다시 학습한 모델로 그렸다.
- **[결과]** 표에 적힌 시험 RMSE(10.22)와 그림·저장 파일의 값(10.53)이 **서로 달랐다.**
- **[원인]** 표는 80% 학습 모델, 그림은 100% 학습 모델이었다.
  숫자 하나에 두 가지 의미가 섞여 있었던 것.
- **[수정]** 조합마다 모델을 두 번 학습하도록 바꿨다.
  - 검증 점수 = 80% 학습 → 20% 설비로 평가 (조합 **선택**용)
  - 시험 점수 = 100% 학습 → 공식 시험 세트로 평가 (최종 **성적**용)
- **[배운 것]** **보고하는 숫자마다 "어떤 데이터로 학습해서 어디에 적용한 값인지"가
  하나로 정해져 있어야 한다.** 0.3 차이라 넘어갈 수도 있었지만,
  이런 애매함이 남아 있으면 나중에 무엇과 무엇을 비교하는지 알 수 없게 된다.

### 3-3. RMSE 만 봤다면 안전 마진을 버렸을 것

- **[시도]** 예측의 **49%가 실제보다 잔여수명을 길게** 보고 있었다.
  현장에서는 곧 고장을 놓치는 것이라, 예측값에서 몇 사이클을 빼는 안전 마진을 검토.
- **[결과]** RMSE 로만 보면 마진은 무조건 손해였다. (9.07 → 9.77 → 12.49 → ...)
  그런데 PHM08 점수로 보면 **마진 5에서 오히려 개선**됐다. (130 → **123**)
  늦게 본 비율은 49% → 28% 로 거의 절반이 됐다.
- **[원인]** RMSE 는 일찍 틀리든 늦게 틀리든 똑같이 취급한다.
  현장의 비용 구조는 전혀 대칭이 아니다 — 늦으면 설비가 멈춘다.
- **[배운 것]** **지표 하나로 판단하면 실무적으로 틀린 결정을 하게 된다.**
  RMSE 만 봤다면 "마진은 성능을 떨어뜨린다"고 결론내고 버렸을 것이다.
  비용 구조를 반영한 지표(PHM08)를 처음부터 같이 놓고 봤기 때문에
  "거의 공짜로 위험을 절반으로 줄이는" 선택지를 찾을 수 있었다.

### 3-4. 건강도 점수를 특징으로 넣는 것이 무의미할 줄 알았는데

- **[시도]** 2단계 건강도 점수를 RUL 예측의 입력 특징으로 추가.
  **효과가 없을 것이라 예상했다.** 건강도 점수는 이미 입력에 들어 있는
  이동평균 특징들로부터 계산되는 값이라, 새로운 정보가 없기 때문.
- **[결과]** RMSE **10.53 → 9.07 (14% 개선).** 72개 특징 중 **중요도 7위.**
- **[원인]** 정보량은 늘지 않았지만, 트리 모델이 스스로 만들기 어려운
  **14개 센서의 비선형 결합(마할라노비스 거리)** 을 미리 계산해 준 셈이었다.
  트리는 축에 수직인 분할만 하므로 이런 조합을 근사하려면 매우 많은 분할이 필요하다.
- **[배운 것]** "정보가 중복되니 의미 없다"는 판단은 **선형 모델 기준의 직관**이다.
  모델이 표현하기 어려운 형태의 조합은, 중복이더라도 미리 계산해 주면 도움이 된다.
  그리고 이 결과로 **단계별 산출물이 다음 단계에서 재사용되는 구조**가 확인됐다.

## 4단계 — 일반화 검증 (운전조건·고장모드 변화)

### 4-1. 계획 변경 — MetroPT-3 를 못 받아서 검증 대상을 바꿈

- **[시도]** 원래 계획은 MetroPT-3(실제 지하철 공기압축기 실측)로 도메인 전이를 검증하는 것.
- **[결과]** 현재 환경에서 UCI 서버 접속이 막혀 데이터 확보 불가.
- **[대안]** C-MAPSS FD002/FD003/FD004 로 검증 대상을 바꿨다.
  이 4개 세트는 **운전조건 수와 고장모드 수가 서로 분리되어** 있어서,
  두 요인 중 무엇이 성능을 무너뜨리는지 **하나씩 떼어내 볼 수 있다.**

  | 세트 | 운전조건 | 고장모드 |
  |---|---|---|
  | FD001 | 1 | 1 |
  | FD003 | 1 | 2 |
  | FD002 | 6 | 1 |
  | FD004 | 6 | 2 |

- **[배운 것]** 데이터를 못 구했을 때 "못 했다"로 끝내지 않고,
  **원래 검증하려던 성질(조건 변화에 견디는가)을 다른 데이터로 확인할 수 있는지**를 먼저 본다.
  결과적으로 이쪽이 오히려 나았다. 요인이 분리되어 있어 원인을 특정할 수 있었기 때문이다.
  MetroPT-3 는 다운로드 스크립트와 절차를 남겨 두어 데이터 확보 시 바로 실행 가능하다.

### 4-2. 고장모드 때문일 것이라 예상했는데 아니었음

- **[시도]** FD001 파이프라인을 나머지 세트에 그대로 적용.
  **고장 유형이 2가지로 늘어난 것이 문제일 것**이라 예상했다.
  한 가지 열화 패턴만 학습한 모델이 다른 패턴을 못 잡을 것이라 생각했기 때문.
- **[결과]** 예상이 빗나갔다.

  | 세트 | 조건 | 고장모드 | RMSE |
  |---|---|---|---|
  | FD001 | 1 | 1 | 10.53 |
  | FD003 | 1 | **2** | **9.28** (오히려 좋음) |
  | FD002 | **6** | 1 | **15.53** |
  | FD004 | **6** | **2** | **16.45** |

- **[원인]** 이 방식은 "정상에서 벗어난 정도"를 보는 것이라
  **어떤 방향으로 벗어나는지(고장 유형)는 상관이 없었다.**
  반면 운전조건은 정상의 기준 자체를 흔들기 때문에 치명적이었다.
- **[배운 것]** 요인이 분리된 데이터가 있으면 **추측하지 말고 나눠서 재면 된다.**
  고장모드가 원인이라고 믿고 모델을 복잡하게 만들었다면 시간만 버렸을 것이다.

### 4-3. 기준선 30사이클이 FD001 에서만 우연히 맞았던 것

- **[시도]** 1~3단계 내내 "설비 초기 30사이클"을 기준선으로 썼다.
- **[결과]** FD002 시험 세트에 관측이 **21사이클뿐인 엔진**이 있었다.
  기준선이 30이면 이 엔진은 **관측 전체가 기준선**이 되어 편차가 항상 0,
  즉 모델이 영원히 건강하다고 판단한다. FD002 6대, FD004 11대가 해당됐다.
- **[원인]** FD001 은 가장 짧은 시험 엔진이 31사이클이라 **우연히 문제가 안 드러났다.**
  하나의 데이터에서 정한 상수가 조용히 깨진 전형적인 경우.
- **[수정]** 설비 길이의 30%(최소 5, 최대 30)로 자동 조절하도록 바꿈.
- **[배운 것]** **하나의 데이터에서 고른 상수는 그 데이터의 성질을 외운 것일 수 있다.**
  다른 데이터로 옮길 때 가장 먼저 깨지는 것이 이런 값이다.
  가능하면 고정값 대신 **데이터에서 유도되는 규칙**으로 쓴다.

### 4-4. 조건 지배도를 재다가 "1경 배"가 나옴 — 자에 재려는 것이 섞여 있었다

- **[시도]** 조건 차이가 열화보다 몇 배 큰지 재기 위해
  `(조건 간 평균 차이) ÷ (열화 폭)` 을 센서마다 계산.
- **[결과 1]** **"최대 1.2경 배"** 라는 말이 안 되는 값이 나왔다.
- **[원인 1]** 애초에 열화가 거의 없는 센서가 분모에 들어갔다. 0 에 가까운 수로 나눈 것.
  → 열화 폭이 표준편차의 20% 미만인 센서는 제외하도록 수정.
- **[결과 2]** 이번엔 FD002 가 통째로 **NaN** 이 됐다. 모든 센서가 걸러진 것.
- **[원인 2]** 필터의 기준으로 쓴 **전체 표준편차 자체가 조건 차이로 부풀려져** 있었다.
  운전조건이 6개면 전체 표준편차의 대부분이 조건 간 차이다.
  그 자로 재니 열화 폭이 실제보다 훨씬 작아 보여 전부 탈락한 것.
  → **조건 내 표준편차**(조건별로 구해 평균)로 바꿔 해결. FD002 중앙 146배, FD004 62배.
- **[배운 것]** **재려는 대상이 자 안에 섞여 있으면 아무것도 못 잰다.**
  정규화에 쓸 기준을 고를 때 "이 기준에 내가 재려는 효과가 들어가 있지 않은가"를 확인해야 한다.
  그리고 비율 지표는 **분모가 의미 있을 때만** 유효하다.

### 4-5. 건강도 점수도 무너졌을 줄 알았는데 멀쩡했음

- **[시도]** RUL 예측이 무너졌으니 2단계 건강도 점수도 무너졌을 것이라 보고 확인.
- **[결과]** 무너지지 않았다. 오히려 **단일 센서 대비 격차가 더 벌어졌다.**

  | 세트 | 센서 1개 | 다변량 건강도 | 격차 |
  |---|---|---|---|
  | FD001 (조건 1) | 0.756 | 0.943 | +0.19 |
  | **FD002 (조건 6)** | **0.580** | **0.914** | **+0.33** |
  | **FD004 (조건 6)** | 0.672 | 0.920 | +0.25 |

  그리고 조건 대책을 적용해도 건강도는 개선되지 않았다 (0.914 → 0.907, 미세 하락).
- **[원인]** 건강도 점수는 이미 조건 효과를 상당 부분 흡수하고 있었다.
  10사이클 이동평균이 여러 조건에 걸쳐 평균을 내고, 설비 기준선도 조건이 섞인 구간에서 잡힌다.
  게다가 AUC 는 순위만 보는 지표라, 조건이 만드는 산포가 정상군과 열화군에
  비슷하게 얹히면 순위가 크게 흔들리지 않는다.
- **[배운 것]** 두 가지다.
  1. **대책은 무너진 곳에만 적용한다.** 안 무너진 곳에 적용하면
     얻는 것 없이 복잡도만 늘고 조금 손해를 볼 수도 있다.
     "좋은 기법이니 전부 적용"은 근거 없는 습관이다.
  2. 실무적으로 더 중요한 결론 — **운전조건이 계속 바뀌는 실제 설비일수록
     고정 임계값 경보는 쓸모없어지고(0.58), 다변량 건강도의 가치는 오히려 커진다(0.91).**
     이 프로젝트에서 현장에 가져갈 근거로 가장 강한 숫자다.

## 5단계 — 현장 적용 파이프라인

### 5-1. 데모 데이터를 120일치로 만들었더니 조건과 시간이 뒤엉킴

- **[시도]** 공조기 모의 데이터를 1월 1일부터 120일치로 생성.
  운전조건(외기온)과 열화(필터 막힘)를 함께 넣었다.
- **[결과]** 막힘이 **시작되기도 전에** 경보가 울리는 설비가 나왔다 (AHU-03 은 12일 전).
- **[원인]** **외기온과 경과시간의 상관이 0.86** 이었다.
  1월에 시작해 4월에 끝나니 시간이 갈수록 더워지기만 한 것이다.
  이러면 "더워진 것"과 "열화된 것"을 구분할 방법이 **원리적으로** 없다.
  게다가 기준선을 초기 구간에서 잡으니 겨울 데이터만으로 기준을 만들고
  여름을 전부 이상으로 판정했다. 기준선 구간 외기온 -3.7~12.1℃ vs 전체 -3.7~29.8℃.
- **[수정]** 2년치로 변경. 1년차는 정상(사계절 전체가 기준선), 2년차부터 열화.
  외기온-시간 상관이 -0.128 로 떨어졌다.
- **[배운 것]** 이건 모의 데이터의 문제가 아니라 **실제 현장에서 그대로 일어나는 문제**다.
  **계절을 타는 설비는 기준선 구간이 최소 1년을 덮어야 한다.**
  겨울에 시운전하고 기준선을 잡으면 여름이 통째로 이상으로 나온다.
  검증용 데이터를 만들 때는 **교란 변수가 시간과 얽히지 않는지** 먼저 확인해야 한다.

### 5-2. 평활 창을 키웠더니 지속 조건이 무력해짐 — 8대 중 7대 오경보

- **[시도]** 시간 단위 데이터라 평활 창을 C-MAPSS 의 10(사이클)에서 24(시간)로 키웠다.
  경보 지속 조건은 24시간 그대로 뒀다.
- **[결과]** **8대 중 7대가 열화 시작 1년 전에 경보.** 평활을 키우기 전보다 훨씬 나빠졌다.
- **[원인]** 평활을 걸면 값이 부드러워지는 대신 **한번 내려가면 오래 머문다.**
  정상 구간의 일시적 이탈도 24시간을 넘기게 되어 지속 조건을 통과한다.
  즉 **평활과 지속 조건은 독립이 아니다.**

  | 평활 창 | 지속 조건 | 열화 전 오경보 |
  |---|---|---|
  | 24시간 | 24시간 (1배) | **7대** |
  | 24시간 | 72시간 (3배) | 0대 |
  | 72시간 | 72시간 (1배) | 3대 |
  | 72시간 | 168시간 (2.3배) | 0대 |

- **[수정]** 지속 조건을 평활 창의 3배 이상으로. 코드에 검사를 넣어
  위반 시 경고가 나오게 했다 (`DetectorConfig.__post_init__`).
- **[배운 것]** **한 파라미터를 바꿀 때 그것과 얽힌 파라미터를 같이 봐야 한다.**
  "평활을 키우면 노이즈가 줄어 좋아질 것"은 한 축만 본 판단이었다.
  그리고 이런 관계는 **규칙으로 못박아 코드에 넣어야** 다음에 안 틀린다.

### 5-3. explain() 에 설명할 행만 넘겼더니 원인이 전부 0σ

- **[시도]** 경보가 난 행 3개만 골라 `explain()` 에 넘겨 원인 분석.
- **[결과]** `급기온도(+0.0σ), 환기온도(+0.0σ), 필터차압(+0.0σ)` — 전부 0.
- **[원인]** `explain()` 이 내부에서 특징을 다시 계산하는데,
  넘긴 3행 안에서 **기준선을 다시 잡았다.** 3행의 평균이 기준선이 되니 편차가 0 이 된다.
  기준선과 이동평균은 **그 설비의 이력 전체**가 있어야 계산된다.
- **[수정]** `explain(df_전체, targets=설명할_index)` 로 인터페이스 변경.
- **[배운 것]** **문맥이 필요한 계산에 일부만 넘기면 조용히 틀린 답이 나온다.**
  에러가 안 나고 0 이 나왔기 때문에, 그림을 안 봤으면 그냥 지나갔을 것이다.
  이런 함수는 인터페이스 자체를 "전체를 받고 일부를 지정" 형태로 만들어야 안전하다.

### 5-4. 그림을 잘못 읽고 "건강도가 요동친다"고 결론낼 뻔함

- **[시도]** 공조기 건강도 궤적을 그렸더니 위쪽 패널이 시커먼 띠로 나왔다.
  "건강도가 시간 단위로 심하게 요동친다"고 판단하고 평활을 키우려 했다.
- **[결과]** 실제로 재보니 **정상 구간 건강도 중앙값은 100** 이었고,
  50 미만은 **4.4%** 뿐이었다. 설정한 오경보율 5%와 거의 정확히 일치한다.
  요동치는 게 아니라 **설비당 17,520점을 다 찍어서** 그렇게 보인 것이었다.
- **[원인]** 2년치 시간 단위 = 설비당 17,520점. 8대면 14만 점.
  이걸 한 축에 다 그리면 4%의 이탈도 검은 띠처럼 보인다.
- **[수정]** 일 단위 중앙값으로 줄여서 그렸다. 그림이 읽히기 시작했다.
- **[배운 것]** **눈으로 본 인상을 결론으로 삼지 말고 재야 한다.**
  하마터면 멀쩡한 설정을 "고치려다" 5-2 의 오경보 사태를 만들 뻔했다
  (실제로 그 순서로 일이 벌어졌다).
  그리고 점을 다 찍는다고 정보가 더 전달되지는 않는다. 적절한 집계가 곧 정보다.
